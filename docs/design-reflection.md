# 架构演进复盘：从缝补状态锁到极简解耦

本文记录从第一代 `mayi-agent` 重构为 `mayi-agent-plus` 的核心架构反思，作为后续迭代防止复杂度反弹的工程备忘录。

---

## 一、第一代架构为什么会陷入“越补越脆”的泥潭？

在第一代实现中，代码库逐渐膨胀出 70+ 个 TypeScript 阶段工作流文件与 45+ 个 Python 模块，其中绝大部分代码都在处理“超时、中断、游标续读、乐观锁冲突、半成品接管”。复盘根因，问题不在大模型本身，而在三个架构错位：

### 1. 把“重型文档解析与 OCR”塞进了模型在线工具调用循环
- **旧做法**：模型每调一次 `read_file(path, page)` 或 `search_sources`，底层临时拉起子进程解析 PDF 单页甚至跑 OCR。
- **连锁副作用**：单页耗时不可控 $\rightarrow$ 被迫加 60 秒单页超时与 1.2 秒搜索软中断 $\rightarrow$ 一次搜不完发明 `next_cursor` 游标 $\rightarrow$ 子代理 30 轮耗尽还没读完 $\rightarrow$ 发明 `partial` 状态、`resume_from` 与 `continuation_targets` 行区间差集算法 $\rightarrow$ 整个会话外层超时被迫拉长到 60 分钟。
- **新架构根治方案**：**解析与推理彻底分家**。通过 `ingest_documents` 一次性多进程把文档离线转为带页码锚点的 `.workspace/parsed/<doc>/full.md` 并按文件 SHA-256 缓存。模型在线面对的永远是微秒级磁盘纯文本，90% 的游标与续派状态机直接归零。

### 2. 用“数据库级事务锁”束缚文档创作
- **旧做法**：要求模型直接输出嵌套极深的 JSON Semantic Blocks（`runs`/`widths`/`s01-id`），并对每个台账和章节强制校验 `expected_sha256`、签发加密 `source_proof`。
- **连锁副作用**：系统提示词膨胀成两百多行的“工具协议说明书”，模型大量推理算力消耗在对齐哈希值和修复 JSON Schema 报错上，真正用于思考工程逻辑与文风质量的注意力反而被稀释。
- **新架构根治方案**：**文件即状态 + Markdown 创作 + 确定性编译器**。中间台账与章节草稿一律采用人类与模型都最擅长的标准 Markdown 文件；并发子代理按独立文件名物理隔离（一人写一章 `.md`），最后由 `docx_builder.py` 确定性地编译为原生 Word 样式对象。

### 3. 把垂直业务硬编码进底座
- **旧做法**：前后端 IPC 协议与工作区底座直接写死 `tender`、`boq`、`construction-plan.json` 等工程招投标概念。
- **新架构根治方案**：底座只保留通用的五步认知进度与五大原子工具，所有招投标、公文报告、数据分析的专业规则一律收敛至 `skills/` 目录。

## 二、新架构的容错边界原则

不做过度复杂的分布式状态机，并不意味着忽视稳定性。`mayi-agent-plus` 只在**真正不可控的外部物理边界**保留三层极简防御：

1. **坏文件隔离（转换层）**：`doc_engine/parser.py` 遇到损坏、加密或纯图片模糊页时绝不崩溃中断整批任务，而是在 `manifest.json` 标记告警信息供模型决策或提示用户。
2. **传输退避重试与截断拦截（模型层）**：`model_factory.py` 统一拦截 HTTP 429 / 5xx 网络抖动做最多 3 次指数退避重试，并严格拦截 `finish_reason == "length"` 防止半截输出污染文件。
3. **落盘自然幂等（文件层）**：解析后的 `.md` 缓存、提取的 `01-requirements.md`、规划的 `02-plan.md` 与各章 `drafts/*.md` 实时落盘。哪怕断电或断网，下一轮会话扫一眼工作区现有文件即可无缝接着往下走。
